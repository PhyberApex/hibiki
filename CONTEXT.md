# Hibiki — Domain Context

Single-context repo (see `agent-docs/domain.md` for how this file is meant to be used). Architectural decisions live in `agent-docs/adr/`.

## Glossary

- **Scene** — a soundboard template (Music, Ambience, Effects categories) stored in `scenes.json`. Not a runtime object; playback state lives in `GuildAudioManager`. See `CLAUDE.md`.
- **Playing Scene** — the Scene started with Play (Discord) or local preview, as distinct from the *open* Scene (the one currently shown in the Scene view). Tracked by `playingSceneId`/`playingSceneMode` in the frontend player store (`frontend/src/stores/player.ts`); survives navigating back to the Scene list. Opening a *different* Scene while one is playing triggers a **Scene Crossfade** rather than losing track of it.
- **Scene Crossfade** — opening a different Scene while one is playing fades the old Scene's Music and Ambience out and the new Scene's in, over the configured fade length (`frontend/src/api/config.ts#fetchSceneFadeLength`, `src/config/scene-fade-settings.ts`), instead of cutting to silence. The new Scene becomes the Playing Scene immediately. An Ambience sound present in both Scenes is never restarted, just glided to its new volume (ambience is already keyed per soundId, not per Scene) — for a backend-decoded Ambience sound (ADR-0003) the renderer does this with `setAmbienceVolume(guildId, soundId, volume, { rampMs })`, letting `GuildAudioManager` ramp the running mixer input directly rather than touching an audio element. Music always has exactly one outgoing and one incoming track. For the renderer fallback path, these are two long-lived, alternating `MusicChannel`s (`frontend/src/views/SceneView.vue`) because capturing an element for Discord permanently binds it, with the ramp/retarget math driven from the renderer by the pure `CrossfadeRamp` class (`frontend/src/audio/crossfade-ramp.ts`). For the backend-decoded path (Music or a non-shared Ambience sound), the renderer just calls `playMusic`/`playAmbience` with `fadeInMs` and `GuildAudioManager` (`src/audio/guild-audio.manager.ts`) fades the previous sound out and the new one in itself, over the same duration — the renderer never ramps an element's volume for it, and only drops its own bookkeeping for the outgoing sound once the new one is confirmed to have started (a failed switch leaves the old one reachable via Stop rather than orphaning it). A fade length of 0 is a hard cut either way. `CrossfadeRamp` ticks on elapsed wall-clock time so a throttled timer still lands on target; a fade already heading out is never redirected back to in.
- **Sound Library** — the GM's own uploaded sound files (`SoundFile`, `src/sound/sound.types.ts`), organized by category (`music` | `effects` | `ambience`). Distinct from the **Registry**.
- **Backend playback** — decoding a Sound Library file straight into PCM in the Electron main process and feeding it to `AudioEngine`'s mixer, instead of the renderer's audio-element → chunked-IPC path. JS/WASM decoders only (`src/audio/decoders/`); a file whose format has no backend decoder (e.g. m4a/AAC) falls back to the renderer path. `sounds.canDecode(type, id)` reports which path applies, decided per sound by `frontend/src/audio/backend-playback-path.ts#selectBackendPlaybackPath` (local preview always stays in the renderer). Music was the first category wired up this way: `playMusic`/`stopMusic`/`setMusicVolume` (`src/player/player.ts` → `GuildAudioManager`) decode straight into the mixer, with live volume changes and fades applied to the running `node-audio-mixer` input rather than re-created on each change. A per-guild generation counter guards against a `playMusic`/Stop race started close together (e.g. a double-click) from resurrecting a track that should have been replaced or stopped. Ambience follows the same shape — `playAmbience`/`stopAmbience`/`setAmbienceVolume`, several active at once per guild keyed by soundId, each with its own generation counter — plus the random-interval repeat (`repeatMin`/`repeatMax` both 0 means a seamless loop; otherwise `GuildAudioManager` waits a random delay in that range after each play-through before restarting the same decoder stream). `getState()`'s `ambience` field lists which soundIds are currently active per guild. See `agent-docs/adr/0003-backend-sound-library-playback.md`.
- **Registry** — the separate curated catalog of community-shared scene bundles (`RegistryEntry`, `registry/`), installable into a user's own scenes via `installFromRegistry`. Registry entries carry their own `tags: string[]`.
- **Sound Tags** — free-form `tags: string[]` on a `SoundFile` (Sound Library), authored manually by the GM per sound. Used for Vibe Matching (see `agent-docs/adr/0001-vision-to-vibe-matching.md`). **Do not confuse with Registry tags** — same field name, different domain object, different purpose (Registry tags describe a shared community scene; Sound Tags describe one of the GM's own files).
- **Vibe Tags** — free-form tags extracted from an uploaded image by a vision-capable model, describing mood, setting, weather, or time-of-day.
- **Vibe Match** — a ranked Sound Library entry (Music or Ambience only) whose Sound Tags overlap with a set of Vibe Tags.
- **Vision Provider** — the model backend that turns an image into Vibe Tags. Two exist: `claude` (default) and `openai-compatible` (any endpoint speaking the OpenAI Chat Completions format, at a GM-configured base URL and model). The GM selects one in Settings; each keeps its own API key. See `agent-docs/adr/0002-vision-providers.md`.
