# Hibiki — Domain Context

Single-context repo (see `agent-docs/domain.md` for how this file is meant to be used). Architectural decisions live in `agent-docs/adr/`.

## Glossary

- **Scene** — a soundboard template (Music, Ambience, Effects categories) stored in `scenes.json`. Not a runtime object; playback state lives in `GuildAudioManager`. See `CLAUDE.md`.
- **Playing Scene** — the Scene started with Play (Discord) or local preview, as distinct from the *open* Scene (the one currently shown in the Scene view). Tracked by `playingSceneId`/`playingSceneMode` in the frontend player store (`frontend/src/stores/player.ts`); survives navigating back to the Scene list. Opening a *different* Scene while one is playing triggers a **Scene Crossfade** rather than losing track of it.
- **Scene Crossfade** — opening a different Scene while one is playing fades the old Scene's Music and Ambience out and the new Scene's in, over the configured fade length (`frontend/src/api/config.ts#fetchSceneFadeLength`, `src/config/scene-fade-settings.ts`), instead of cutting to silence. The new Scene becomes the Playing Scene immediately. An Ambience sound present in both Scenes is never restarted, just glided to its new volume (ambience is already keyed per soundId, not per Scene) — for a backend-decoded Ambience sound (ADR-0003) the renderer does this with `setAmbienceVolume(guildId, soundId, volume, { rampMs })`, letting `GuildAudioManager` ramp the running mixer input directly rather than touching an audio element. Music always has exactly one outgoing and one incoming track. For the renderer fallback path, these are two long-lived, alternating `MusicChannel`s (`frontend/src/views/SceneView.vue`) because capturing an element for Discord permanently binds it, with the ramp/retarget math driven from the renderer by the pure `CrossfadeRamp` class (`frontend/src/audio/crossfade-ramp.ts`). For the backend-decoded path (Music or a non-shared Ambience sound), the renderer just calls `playMusic`/`playAmbience` with `fadeInMs` and `GuildAudioManager` (`src/audio/guild-audio.manager.ts`) fades the previous sound out and the new one in itself, over the same duration — the renderer never ramps an element's volume for it, and only drops its own bookkeeping for the outgoing sound once the new one is confirmed to have started (a failed switch leaves the old one reachable via Stop rather than orphaning it). A fade length of 0 is a hard cut either way. `CrossfadeRamp` ticks on elapsed wall-clock time so a throttled timer still lands on target; a fade already heading out is never redirected back to in by the ramp itself, so a Scene Crossfade back to a Scene that wants a renderer-fallback Ambience sound still fading out cancels that out-fade and glides it back in from its current volume. The Music half of this machinery (one outgoing, one incoming track, over the Scene fade length) is also what a **Music Mode** advance and a manual jump within one Scene use; see `agent-docs/adr/0006-renderer-driven-music-advance.md`.
- **Music Mode** — how a Scene moves through its Music list: **single** (one track, the initial and only behaviour until now: the first track plays and, if its Loop toggle is on, repeats), **sequential** (tracks play in list order, wrapping from the last back to the first) or **shuffle** (a shuffle bag: every track plays once in random order before any repeats, reshuffled each pass, never the same track twice in a row). In sequential and shuffle the **advance** happens when the current track plays out: the next track starts with the Scene fade length as its fade-in (0 is a hard cut); there is no overlap with the outgoing track, because the backend playback path does not know a track's duration ahead of time. The per-track Loop toggle only exists in single mode; the other modes hide and ignore it, leaving the stored value intact. The Music Mode belongs to the Scene: stored in `scenes.json`, carried in `.hibiki.zip` exports and Registry bundles, with single as the default when absent. Every way of starting a Scene (Play, Scene Crossfade, Scene Hotkey, Previous/Next Scene) starts Music the same way: the first track in single and sequential, a random one in shuffle. Clicking a Music track's Play while the Scene's Music plays is a **jump**: a Scene-Crossfade-style switch to that track, after which the mode continues from it (sequential: its successor; shuffle: a fresh bag without it). The mode applies to whichever Scene the current track was started from, whether or not that Scene is the Playing Scene, and the advance reads the Scene's live Music list at the moment it advances (tracks added, removed or reordered mid-session take effect at the next advance; an emptied list means Music ends after the current track). A track that cannot start (missing sound, decode failure) is skipped; after a full pass with nothing playable Music goes silent. Stop on the Music card stops Music without touching the mode. See issue #539 and `agent-docs/adr/0006-renderer-driven-music-advance.md`.
  _Avoid_: playlist, playlist mode, queue, repeat mode, autoplay
- **Output Target** — where a Scene's mixed audio is heard: a **Discord Target** (the bot in one voice channel of one guild) or the **Local Target** (the GM's own speakers, for an in-person table). Every playback call is addressed to exactly one Output Target; the Target, not a Discord guild, is the unit that owns playback state (what is playing, volumes, Ambience intervals, Effect Instances). A Discord guild is one kind of Output Target, and the Local Target exists even when no Discord token is configured. Exactly one Output Target is active at a time; the GM switches it from the Scene view and the choice persists across launches. Playing a Scene, toggling one Ambience sound or tapping an Effect all go to the active Target. Switching the active Target while a Scene is playing is a hard handover: the Scene stops on the old Target and restarts from the top on the new one, with no cross-Target fade. A Sound Library file with no backend decoder is heard natively from the renderer under the Local Target rather than passing through the mix; a Browser tab reaches either Target only as a Routed Tab. The Local Target is a full peer of a Discord Target (same decoding, loops, intervals, fades, Effect Instance cap), not a preview. See `agent-docs/adr/0004-local-output-target-renderer-sink.md`.
  _Avoid_: local preview, preview mode, output mode, local guild, pseudo-guild
- **Output Device** — the physical or virtual audio output (built-in speakers, a USB speaker, a second sound card) the Local Target plays through, chosen by the GM in Settings. It belongs to the Local Target only; a Discord Target has no Output Device because Discord delivers its mix. "System default" is a valid choice and the initial one. The choice is personal to the GM's machine and persists across launches. A change applies immediately, even mid-Scene. If the chosen Output Device is absent when local playback starts or disappears while playing, the Local Target plays through the system default and tells the GM, keeping the choice so it resumes once the device is back. The m4a fallback and a Routed Tab follow the Output Device; a Browser tab that is not routed plays through the system default. See issue #537.
- **Routed Tab** — a Browser tab whose audio is sent to the **active Output Target**, toggled per tab by the GM from the Browser toolbar. Under a Discord Target it is streamed into the guild's mix; under the Local Target it is heard through the Output Device at the Target's level instead of raw from the page. A tab that is not routed plays raw on the GM's machine, untouched by any volume, under either Target. A Routed Tab follows the active Target with the same hard handover as the Playing Scene (stops on the old Target, resumes on the new one, waiting for a joined channel under Discord) and is independent of the Scene lifecycle: Scene Stop, the Stop Hotkey and Stop all Effects leave it alone; only the GM's toggle, closing the tab or a Target handover ends it. Routing is machine-local session state, never persisted. See `agent-docs/adr/0007-routed-tab-local-capture.md`.
- **Tab Volume** — the 0–100 level of one Browser tab, shown in the Browser toolbar for the active tab, default 100, kept per tab for the life of the tab and never persisted. It applies only while the tab is a Routed Tab and combines with the active Target's Master volume exactly as a Scene item's own volume does (both scale the level that reaches the Target; the master changes a Routed Tab live, including from the Volume Up / Volume Down Action Hotkeys).
  _Avoid_: sink (as a domain term; the sink is the renderer mechanism), speaker, audio output, sinkId
- **Sound Library** — the GM's own uploaded sound files (`SoundFile`, `src/sound/sound.types.ts`), organized by category (`music` | `effects` | `ambience`). Distinct from the **Registry**.
- **Backend playback** — decoding a Sound Library file straight into PCM in the Electron main process and feeding it to `AudioEngine`'s mixer, instead of the renderer's audio-element → chunked-IPC path. JS/WASM decoders only (`src/audio/decoders/`); a file whose format has no backend decoder (e.g. m4a/AAC) falls back to the renderer path. `sounds.canDecode(type, id)` reports which path applies, decided per sound by `frontend/src/audio/backend-playback-path.ts#selectBackendPlaybackPath` (local preview always stays in the renderer). Music was the first category wired up this way: `playMusic`/`stopMusic`/`setMusicVolume` (`src/player/player.ts` → `GuildAudioManager`) decode straight into the mixer, with live volume changes and fades applied to the running `node-audio-mixer` input rather than re-created on each change. A per-guild generation counter guards against a `playMusic`/Stop race started close together (e.g. a double-click) from resurrecting a track that should have been replaced or stopped. Ambience follows the same shape — `playAmbience`/`stopAmbience`/`setAmbienceVolume`, several active at once per guild keyed by soundId, each with its own generation counter — plus the random-interval repeat (`repeatMin`/`repeatMax` both 0 means a seamless loop; otherwise `GuildAudioManager` waits a random delay in that range after each play-through before restarting the same decoder stream). Effects followed last — `playEffect`/`stopEffects`, every trigger its own mixer input rather than replacing a previous one, layering freely up to 8 simultaneous instances per guild (oldest evicted first), served from an in-memory PCM cache (`src/audio/decoders/effect-pcm-cache.ts`) shared across guilds to keep trigger latency low. `getState()`'s `ambience` field lists which soundIds are currently active per guild. See `agent-docs/adr/0003-backend-sound-library-playback.md`.
- **Effect Instance** — one playing occurrence of an Effect sound, created per trigger, with its own duration and lifetime, independent of other instances of the same sound (see "Backend playback" above — Effects already layer freely up to 8 per guild). The Scene view's Effect card shows every active instance of a sound as a progress fill + `m:ss / m:ss` timer tracking whichever instance will finish *last*, plus a `×N` count badge once more than one is active, and a Stop control that ends every instance of that sound across whichever path(s) they're playing on. All three playback paths (backend-decoded, the renderer's Discord-fallback, and local preview) report instances the same way: `frontend/src/stores/player.ts` holds one reactive, per-instance map merging backend-reported instances (synced from `getState()`'s `effects` field and the `stateChanged` push, which fires on every instance start and end) with renderer-tracked ones (registered directly by `SceneView.vue` for the fallback/local-preview paths, since the backend has no visibility into those). Progress between `stateChanged` edges ticks on the renderer's own clock rather than polling the backend. Backend-decoded duration is known before playback starts — `src/audio/decoders/effect-pcm-cache.ts` always decodes the whole file first, so its byte length divided by the fixed PCM byte rate gives the duration with no decoder changes; the renderer-tracked paths read it off their own `<audio>` element once loaded. `player.playEffect`/`GuildAudioManager.playEffect` resolve with the new instance's id and duration; `player.stopEffect`/`GuildAudioManager.stopEffect` end one instance by id (a no-op if already ended) — distinct from the existing guild-wide `stopEffects`, which still backs Scene stop/leave/disconnect. See issue #509.
- **Hotkey** — a system-wide key binding (an Electron `globalShortcut` accelerator) that drives playback while any other window has focus, so a Stream Deck, macro keyboard or foot pedal can control Hibiki by emulating a keystroke. Every Hotkey acts on the **active Output Target**; no Target is stored on a binding. Hotkeys never move keyboard focus or navigate the UI; the Playing Scene indicator is the only on-screen feedback. Three kinds exist: a **Scene Hotkey** (owned by one Scene, global; pressing it plays that Scene, which is a Scene Crossfade if another Scene is playing, and stops it if that Scene is already the Playing Scene), an **Effect Hotkey** (owned by one Effect item inside a Scene, live only while that Scene is the Playing Scene, so different Scenes may reuse the same key for their own Effects) and the **Action Hotkey** family (see below). Within Hibiki a key may not be shared by two Scenes, by two Effects of the same Scene, or by an Effect and any Scene or Action Hotkey, nor by two Action Hotkeys. Hotkeys are personal to the GM's machine: stored on the Scene in `scenes.json` but stripped from `.hibiki.zip` exports and never present in Registry bundles. A global "Enable global hotkeys" setting hands every key back to the OS without unbinding. A Hotkey the OS refuses (held by another app, or no support as on Wayland) is reported, never silently dropped. See `agent-docs/adr/0005-global-hotkeys-as-external-control-surface.md`.
- **Action Hotkey** — a Hotkey bound to one fixed app action, owned by nobody and kept in the hotkey settings (Settings → Hotkeys) rather than on a Scene. Six exist, all acting on the **active Output Target**: **Stop Hotkey** (stops the Playing Scene; a no-op when none plays), **Stop all Effects** (ends every Effect Instance, whether or not a Scene plays; a no-op with none), **Volume Up** / **Volume Down** (move the Target's master volume by 5, clamped at 0 and 100, persisted even with nothing playing or no Discord channel joined; a press at the bound is a no-op; feedback is one "Master volume N%" toast that updates in place), and **Previous Scene** / **Next Scene** (anchored on the Playing Scene, never the open Scene, and a Scene Crossfade like a Scene Hotkey; with no Playing Scene Next starts the first Scene and Previous the last; order is the Scene list as displayed (`scenes.json` order); no wrap, so Next on the last and Previous on the first are no-ops). Silent no-ops are logged at debug.
  _Avoid_: keybind, shortcut, global shortcut (as a domain term), Stream Deck integration, deep link
- **Master volume** — the single 0–100 slider in `SceneView.vue` (`globalVolume`), one value per Output Target (the slider shows the active Target's), that scales every per-item volume, for Music, Ambience and Effects alike, on both the backend-decoded and renderer-fallback paths (`computeVolume()`). Persisted in `app-config.json` via the `config` IPC domain's `getMasterVolume`/`setMasterVolume` (`src/config/master-volume-settings.ts`), loaded once on mount instead of resetting to the default every launch. Neither `player` nor `AudioEngine` has a master-volume concept — they only ever receive an already-scaled absolute volume per call; a guild-level `music`/`effects` volume API existed briefly during the backend-playback migration (#414) but was dead code (nothing ever called it) and was removed in #419.
- **Registry** — the separate curated catalog of community-shared scene bundles (`RegistryEntry`, `registry/`), installable into a user's own scenes via `installFromRegistry`. Registry entries carry their own `tags: string[]`.
- **Sound Tags** — free-form `tags: string[]` on a `SoundFile` (Sound Library), authored manually by the GM per sound. Used for Vibe Matching (see `agent-docs/adr/0001-vision-to-vibe-matching.md`). **Do not confuse with Registry tags** — same field name, different domain object, different purpose (Registry tags describe a shared community scene; Sound Tags describe one of the GM's own files).
- **Vibe Tags** — free-form tags extracted from an uploaded image by a vision-capable model, describing mood, setting, weather, or time-of-day.
- **Vibe Match** — a ranked Sound Library entry (Music or Ambience only) whose Sound Tags overlap with a set of Vibe Tags.
- **Vision Provider** — the model backend that turns an image into Vibe Tags. Two exist: `claude` (default) and `openai-compatible` (any endpoint speaking the OpenAI Chat Completions format, at a GM-configured base URL and model). The GM selects one in Settings; each keeps its own API key. See `agent-docs/adr/0002-vision-providers.md`.
- **Usage Stats** — anonymous, opt-in counts of how Hibiki is used (which views and features are reached, on which OS and app version), sent to the project's self-hosted Umami instance only after the GM switches them on in Settings; off by default, with a single, never-repeated first-run invitation. The set of events is fixed and listed in full on the public privacy page; no identifier is stored on the machine, so switching off leaves nothing to delete. Never carries guild, channel, Scene, sound or Hotkey names, URLs or anything else the GM authored. Dev, test and unpackaged builds never send. Distinct from **Diagnostics** (`hibiki.log`), which stays on the machine and is only ever shared by the GM by hand.
  _Avoid_: telemetry, analytics, tracking, metrics
