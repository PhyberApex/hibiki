# 0003. Backend Sound Library playback: main-process JS/WASM decoders

## Status

Accepted

## Context

Issue #414 moves Sound Library playback for Discord into the Electron main process: the backend decodes Music, Ambience and Effects files straight into the per-guild mixer (`AudioEngine`, `src/audio/audio-engine.ts`) and owns playback state per guild, as `CLAUDE.md` already (aspirationally) describes. Today none of that exists — `src/player/player.ts` only exposes `startStream`/`startEffectStream`, and all Scene playback happens in the renderer via `HTMLAudioElement` + chunked IPC (`frontend/src/views/SceneView.vue`).

The work is split into sub-issues, chained with blocked-by, so each lands as one focused agent run:

1. Issue #415 (this ADR) — ADR and the decoder module, no GM-visible behaviour change.
2. Issue #416 — Music
3. Issue #417 — Ambience
4. Issue #418 — Effects
5. Issue #419 — Master volume, cleanup and docs

This ADR, numbered 0003 because ADR-0002 (Vision Providers) already exists, records the decisions from #414's triage that apply to the decoder foundation, ahead of #416–#419 wiring it into actual playback.

## Decision

- **Where decoding happens**: in the Electron main process. A Sound Library file is read from disk and decoded straight into PCM that feeds `AudioEngine`'s `node-audio-mixer` inputs (48 kHz, stereo, signed 16-bit little-endian). Playback state stays per guild in `GuildAudioManager`.
- **Decoders: JS/WASM only, no bundled ffmpeg binary.** Four small packages from the `wasm-audio-decoders` family cover the required formats, each shipping its WASM binary base64-embedded in its JS bundle (no separate `.wasm` file I/O, so no asar-unpacking is needed for them — see `forge.config.js`'s `asar.unpack`, which only covers native `.node` modules like `@snazzah/davey`, Discord's DAVE E2EE voice encryption):
  - `mpg123-decoder` — MP3
  - `@wasm-audio-decoders/ogg-vorbis` — Ogg Vorbis
  - `ogg-opus-decoder` — Ogg Opus (used with `forceStereo: true`; libopus always decodes at 48 kHz, so this path needs no sample-rate conversion, only channel up-mixing)
  - `@wasm-audio-decoders/flac` — FLAC
  - WAV has no decoder package — a hand-rolled RIFF chunk walker (`src/audio/decoders/wav-decoder.ts`) reads past arbitrary chunks (e.g. the `LIST`/`INFO` metadata chunk ffmpeg writes before `data`) to find the `data` chunk, then converts PCM/IEEE-float samples of any supported bit depth directly.
  - **Packaging caveat, verified before committing to these packages**: all four are ESM-only (`"type": "module"`), while this repo's backend compiles to CommonJS (`tsconfig.json`'s `"module": "commonjs"`). A plain `import` of an ESM-only package compiles to `Promise.resolve().then(() => require(...))`, and `require()` of an ESM module only works because Node 24 (already required — see `.nvmrc`, `package.json#engines`, and CLAUDE.md's Node-version rule) supports synchronous `require(esm)` natively; this was confirmed to work both via `tsc --build` and inside the compiled `dist/` output. Jest, however, gates its own equivalent support behind Node's `--experimental-vm-modules` flag (it probes for `vm.SourceTextModule`, which only exists with that flag), so `test:backend`/`test:watch`/`test:coverage:backend` in `package.json` now run `node --experimental-vm-modules node_modules/.bin/jest` instead of invoking `jest` directly — otherwise Jest throws `ERR_REQUIRE_ESM` the moment a spec imports the decoder module.
  - `ogg-opus-decoder` pulls in `@wasm-audio-decoders/opus-ml` (~8 MB unpacked) as a dependency for an optional speech-quality-enhancement mode this project doesn't use; it's lazy-loaded (`import(/* webpackChunkName: "opus-ml" */ ...)`) only when the `speechQualityEnhancement` option is passed, which Hibiki never does, so it adds to on-disk `node_modules`/packaged size but is never evaluated at runtime.
- **Streaming, not whole-file buffering**: every decoder here accepts chunked input (`decode(chunk)` called repeatedly, `flush()` at the end for the three `wasm-audio-decoders` packages), so `src/audio/decoders/read-chunks.ts` reads the source file in fixed-size chunks (`fs.createReadStream`) instead of loading it whole. The WAV reader streams the `data` chunk the same way via positioned `FileHandle.read()` calls. A single stateful `PcmResampler` (`src/audio/decoders/pcm-resample.ts`, linear interpolation, phase carried across `push()` calls) turns each decoded chunk — at whatever native sample rate/channel count the file has — into continuous 48 kHz stereo PCM, so chunk boundaries don't click or reset resampling phase.
- **Backpressure into the mixer (`src/audio/mixer-feed.ts`)**: `node-audio-mixer`'s `AudioInput` acknowledges every write immediately and holds whatever it is given, so piping a decoder straight into it has no backpressure — a multi-minute track is decoded into memory whole within a second or two, the source `Readable`'s `end` fires then rather than when the audio has played, and the input bakes `params.volume` into bytes as they are written, so later volume changes never reach what is already queued. Combined with the loop/interval-repeat restarts in `GuildAudioManager`, which were keyed off that `end`, this produced a runaway: a looping track re-decoded itself every second into a fresh layered input until allocation failed (`Array buffer allocation failed`, reported from Windows). `feedMixerInput` therefore reads the source in paused mode and keeps at most `DEFAULT_LEAD_MS` (300 ms) of PCM queued in the input, topping it up on a 20 ms poll; the source's own `highWaterMark` then carries the backpressure into the decode loop (`createProducerStream`). Every slice handed to the input is an exactly-sized, unpooled copy because the mixer processes a chunk through `chunk.buffer` (the whole underlying `ArrayBuffer`), not the view. `AudioEngine.playMusicFromStream` takes an `onEnded` callback that fires only once the source has ended *and* the input has drained (or the source errored), and that is what `GuildAudioManager` keys loop/repeat restarts and track clearing off — never the raw source `end`. Stopping a stream sets `forceClose` on the input before destroying it so the cut is immediate; without it a destroyed input keeps playing until its queue empties.
- **Mixing concurrent inputs needs a packet-sized mixer `highWaterMark`**: without one, every `node-audio-mixer` tick takes `min(dataSize)` over its *non-empty* inputs from each of them and leaves empty inputs out of the sum entirely. Each `feedMixerInput` refills its own input on its own 20 ms poll, so with Music and Ambience running together the mixer regularly ticks while one input has just been refilled and the other has not, drains that one solo, then does the same for the other: measured as only ~25 % of output samples carrying both inputs, the rest alternating solo bursts of up to the 300 ms lead (heard as heavy stutter as soon as a second sound starts; a lone sound is unaffected). `AudioEngine` therefore sets `highWaterMark: MIXER_PACKET_BYTES` (3840 bytes, one 20 ms Discord packet), which makes a tick take exactly one packet from every input holding at least one, so the mix is complete as long as each feed keeps its input topped up. Because the mixer then never takes a partial packet, `feedMixerInput` pads a source's trailing partial packet with silence before ending the input; otherwise the tail would sit in the input forever and `onEnded` (which loop and interval restarts hang off) would never fire. `src/audio/mixer-concurrency.spec.ts` drives the real mixer with two deliberately out-of-phase feeds and asserts every output sample carries both, including with every timer clamped to a 15 ms Windows tick.
- **Keeping the voice player alive, and silence as the player's job (`AudioEngine`)**: `node-audio-mixer` drives itself from a 1 ms `setTimeout` loop and, with `generateSilence`, emits a silence frame on every tick that finds its inputs momentarily empty. That caused two bugs. On Windows, which honours a 1 ms timer at roughly 15 ms granularity, the library default of 1 ms of silence per tick produced silence at a fraction of real time; once the ~170 ms buffered in the output `PassThrough` drained, `@discordjs/voice`'s `AudioPlayer` hit its default `maxMissedFrames` (5 frames, 100 ms) and stopped the resource about 300 ms after the connection became ready and before any sound was started — and the engine only ever called `play()` once, so the bot stayed silent for the whole session with no voice activity shown. Everywhere, the same generator chopped silence into music: between the 20 ms feed refills, ticks that found the input empty inserted silence frames mid-track (measured as ~30 % of the output being silence with 20 ms frames on a 1 ms tick). The mixer therefore runs with `generateSilence: false`; when no input has data it simply produces nothing, and the voice player sends its own silence frames, which is what it does anyway whenever `read()` returns no packet. `maxMissedFrames` is `Infinity` so a quiet mixer is never mistaken for a finished track, each fresh mixer output is primed with one 20 ms silence frame so the player leaves `buffering` immediately, and if the player ever does reach `idle` while the engine is alive, `attachMixerOutput` rebuilds the output `PassThrough` and resource and plays again (stopping a resource destroys its whole `pipeline`, mixer output included), logging an error line so the event is visible in `hibiki.log`. Verified by clamping every `setTimeout` to 15 ms locally: the old configuration missed 139 of 296 Opus packets in runs of 15; the new one misses none, and the share of audible samples in the mixer output equals that of the raw decode (85.5 %) under both normal and clamped timers.
- **Ogg container ambiguity**: a `.ogg`/`.oga`/`.opus` file can hold Vorbis or Opus; the extension alone doesn't say which. `src/audio/decoders/ogg-sniff.ts` reads the first Ogg page (a few KB at most) and looks for the `OpusHead` or `\x01vorbis` codec-identification marker before picking a decoder.
- **Formats with no backend decoder (m4a/AAC, and anything else)**: `canDecode()` returns `false`; no native dependency is added to support them. Per #414, those files keep playing through today's renderer path (audio element → chunked IPC) — nothing in an existing library stops working. Local preview (not in a voice channel) also stays in the renderer per #414, unaffected by this ADR.
- **Surfacing the capability**: `sounds.canDecode(type, id)` is exposed over IPC (`src/bootstrap-embedded.ts`, wrapped in `frontend/src/api/sounds.ts`) so #416–#419 can route an individual sound to the backend-decode path or the renderer fallback. This issue only adds the capability check — no playback code calls it yet, so there is no GM-visible behaviour change.
- **Overlapping Effects (#408) and Scene crossfade (#409)**: both already shipped in the renderer before this ADR. Nothing here changes `AudioEngine`'s per-stream-id model (`playMusicFromStream`/`playEffectFromStream`, `src/audio/audio-engine.ts`), which both behaviours depend on; #416–#419 are responsible for preserving them when wiring actual playback through these decoders.

## Consequences

- Four new runtime dependencies (plus their shared `@wasm-audio-decoders/common` and the unused `opus-ml` chunk), all WASM-in-JS with no native/.node binaries — no new asar-unpacking rules needed, unlike `@snazzah/davey`.
- The ESM/CommonJS interop relies on Node 24's `require(esm)` support, which is already a hard requirement for this project (Electron 41+ needs Node 24+) — no new minimum-version constraint, but it is now also load-bearing for decoding, not just for running tooling.
- `pnpm test`/`pnpm test:watch`/`pnpm test:coverage` now launch Jest via `node --experimental-vm-modules node_modules/.bin/jest` instead of the `jest` bin directly; this is Jest's documented, non-breaking way to support `require(esm)`, and produces identical results for every existing spec.
- Mono sources are up-mixed to stereo (duplicated to both channels) and anything beyond two channels is read as its first two; Hibiki's own uploads are expected to be mono or stereo, so this is not expected to matter in practice.
- Volume changes on a backend-decoded stream (`setStreamVolume`/`rampStreamVolume`) become audible after roughly the queued lead plus the mixer→`AudioResource` pipeline, about half a second; a crossfade is a little blunter than in the renderer, accepted in exchange for bounded memory.
- `PcmResampler`'s linear interpolation is adequate for mixing voice-channel audio (sound effects, ambience loops, background music) but is not broadcast-quality band-limited resampling; accepted as proportionate to the use case.
